# IPC Section Assistant (v8.1): Features

An offline legal assistant for Indian court judgments. You give it a judgment (PDF) and it:

1. Proposes the IPC sections that apply.
2. Explains the judgment in a fixed four-part format.
3. Lets you chat with the document.

Everything runs on a laptop GPU. After the one-time model download, nothing leaves the machine.

---

## 1. The core model: Hyena + Llama hybrid (v7 checkpoint)

| Stage | What it does | Model |
|---|---|---|
| **1 · Sentence reader** | Turns every sentence of the judgment into a vector | InLegalBERT (`law-ai/InLegalBERT`, pretrained on Indian legal text, frozen) |
| **2 · Hyena encoder** | Reads the **whole** judgment (up to 16,384 tokens) and scores all 100 IPC sections | Hyena long-convolution encoder (512-dim, 4 layers, ensemble of 3), with a label-correlation layer in which sections attend to each other |
| **3 · Shortlist** | Keeps the top 5–10 candidates (drops those below 5%) | — |
| **4 · Verifier** | Reads the opening plus key passages (~2.5k tokens) and answers yes/no for each candidate | Llama-3.2-3B-Instruct, 4-bit, with a fine-tuned LoRA |
| **5 · Fusion** | Combines encoder and verifier scores (α = 0.6, threshold 0.35) | — |

**Why a hybrid:** Llama alone runs out of memory at 32k tokens. In the hybrid, Hyena reads everything and Llama only reads ~2.5k tokens, so memory stays at about 4.3–4.6 GB whatever the judgment length (measured from 2k to 32k tokens).

**Training data:** Indian Supreme Court judgments 2005–2024, split by time: train ≤ 2020, dev 2021–22, test ≥ 2023. Labels are the 100 most frequent IPC sections. Half the training documents had the sentences that cite sections removed, so the model learns from the facts rather than from citations.

### Results (test split, 150 judgments)
| System | Precision | Recall | Micro-F1 |
|---|---|---|---|
| Llama zero-shot (lists sections) | 0.309 | 0.262 | 0.283 |
| Fine-tuned Llama (lists sections) | 0.512 | 0.279 | 0.361 |
| Hyena encoder only | 0.584 | 0.543 | 0.563 |
| Fine-tuned verifier on the encoder shortlist | 0.687 | 0.470 | 0.558 |
| **Hybrid fused, one threshold (deployed)** | **0.606** | **0.561** | **0.583** |

- **Top-20 most frequent sections:** micro-F1 0.658.
- **Facts-only view** (section citations hidden): 0.582. The model works almost as well without seeing the citations.
- **Ranking:** precision@1 0.853; recall@10 0.786. The correct section is usually in the shortlist.
- **By length:** short ~4k tokens 0.577 · medium ~8k 0.607 · long ~18k 0.526.

## 2. Explanation (v8.1)

- A fixed **four-part explanation** generated by the chosen chat model. If the model stops before part 4, the engine asks it once to finish.
- **Every claim cites a sentence** as `[S12]`; click one in the web app to read that sentence.
- **The model must use only the context:** it writes "not stated in the judgment" where something is missing, and support for a claim needs a quoted `[S#]`.
- **Case facts are extracted by code, not by the model** (`ipc/case_facts.py`):
  - Charges are grouped by Act (BNS, IPC, POCSO, SC/ST, …).
  - Case number and parties come from the first-page header.
  - The PROCEEDINGS block covers the FIR and dated hearings.
  - The full operative order is included (up to 3,500 characters).
  - Charges are checked against the predicted sections, including IPC → BNS mapping (e.g. IPC 376 → BNS 64).
- **Role-aware output** (accused / other roles; set in `settings.json`).

## 3. Chat with the judgment + Bayesian router

- **A Bayesian network decides how to answer every question.** It has 20 nodes (14 signals → 4 bottlenecks → risk → route) and estimates P(wrong answer) by exact inference:
  - **Serve** (< 0.20): answer from the judgment.
  - **Search** (0.20–0.60): search the offline library.
  - **Clarify** (> 0.60): ask you a clarifying question.
- **Runs on the CPU only** (~60 ms per question), so it never competes with the GPU.
- **Retrieval:** InLegalBERT plus BM25, with distance cut-offs recalibrated for InLegalBERT.
- **Offline library** (`legal_kb`): 100 statute cards, 250 passages from 50 judgments, and CrPC/BNSS procedure cards.
- **Guard against borrowed facts:** passages from other cases are dropped when a question is about *this* case.

## 4. Pluggable chat models

- **Any Ollama model** (read live from `ollama list`). The choice is remembered in `settings.json`.
- **`builtin`:** the local Llama-3.2-3B with the verifier LoRA switched off for chat, and a KV cache reused across turns.
- **`none`:** extractive answers built directly from the retrieved passages.
- **Automatic GPU memory handover:** the engine unloads the verifier or the Ollama model so the two never share the GPU at once.

## 5. Interfaces

| Interface | Features |
|---|---|
| **Web app** (`:7860`) | Drop in a PDF, watch each stage, see sections with confidence and evidence, a streamed explanation, and chat with route badges |
| **Architecture page** (`/architecture`) | **Explain** mode: click any block for what it does, where the code is, and whether it runs on CPU or GPU; play with the real 20-node network. **Live** mode: blocks light up with real timings, shortlist, router decision and speed |
| **Terminal UI** (`tui.py`) | Inline `/` command menu with autocomplete, an `/open` file browser, history, a status line, and per-stage timings. Commands: `/explain /sections /candidates /evidence /passages /route /kb /proceedings /model /verifier /gpu /paste` |
| **CLI** (`analyse.py`) | One-shot analysis of a file or a whole folder, with JSON output |
| **HTTP API** | `/api/analyse` `/api/explain` `/api/chat` (server-sent events), plus state, models, KB, graph and Bayes endpoints |

**One copy of the models is shared between interfaces.** The TUI attaches to a running server, and a judgment opened in one interface shows up in the others.

## 6. Performance (RTX 3050, 12-page judgment)

| | v7 | v8 |
|---|---|---|
| Model pipeline | 22.1 s | **5.7 s** |
| Upload → sections shown | 42–59 s | **5.7 s** (explanation streams, first token ≈ 4 s) |
| Server start | ≈ 34 s | 10–14 s (pre-quantised 4-bit cache) |
| Re-opening the same judgment | full re-run | instant (result cache) |
| Hyena-only mode | — | 0.56 s, 0.4 GB VRAM |
| Peak VRAM | 2.98 GB | 3.06 GB |

The v8 speed-ups come from three changes: InLegalBERT on the GPU in fp16, a shared-prefix KV cache in the verifier, and a 4-bit model cache on disk.

## 7. Robustness

- **Scanned PDFs:** automatic in-process OCR fallback when a page has fewer than 50 words of extractable text.
- **Low GPU memory:** if loading fails, the web page names the program that is in the way and offers a Retry button.
- **CPU-only fallback:** works without an NVIDIA GPU (~14 GB RAM, minutes per judgment).
- **Tests:** Bayes network (checked against pgmpy, max difference 5e-5), retriever on CPU only, score parity of the pipeline, and an end-to-end engine test.

## 8. Known limits

- **Explanation and chat quality depend on the chat model.** A 3B model sometimes paraphrases loosely, which is the main target for improvement.
- **Labels are IPC only** (100 sections). BNS appears only through mapping.
- **Rare sections are weak:** macro-F1 is 0.33.
- **The router's signal extractors are heuristics,** so some questions are routed more cautiously than a human would.
- **Decision support only:** a qualified lawyer must verify every section.
